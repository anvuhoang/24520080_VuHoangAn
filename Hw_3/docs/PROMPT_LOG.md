## Lessons Learned

1. **A late timer is the whole problem of a countdown.** Anything that subtracts one per tick is wrong the first time the main thread is busy; a value computed from the clock is right whenever it is asked. The design is "compute, then decide when to look", and a test that moves the clock BEFORE letting the timer run is the one that tells the two apart.
2. **Do not trust the device clock, and do not trust it before the server has answered either.** A device an hour ahead would have closed the window on a page that was still open. Both directions were tested, in unit tests and in Chrome.
3. **The server must be the judge.** Chrome showed a page whose window had been closed by the server under it: the countdown still said 1 day, the form was open, and the server answered 403 and the page said so. The countdown is only a display.
4. **A test that was left out to make the run pass is a bug that was kept.** `a@b..` is a real address problem; it was found because the case was written down, not because it failed.
5. **A real browser finds what jsdom cannot.** A 404 for a normal "no" is silent in tests and loud in the console of every visitor.
6. **Read each surviving mutant before writing a test.** Two of the nine were the same behaviour guarded twice; the first one pointed at a comment and not at the code.
7. **A fake that follows the server's rules is worth its weight.** The fake API uses the same `validateAppeal` and judges the deadline by its own clock, so the page tests cover the 400, 403 and 409 paths with real logic and not with canned answers.
